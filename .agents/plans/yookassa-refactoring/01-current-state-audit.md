# Доработка и рефакторинг модуля YooKassa

> **Область:** обработка отменённых платежей, рефакторинг PaymentService,
> аудит модели Payment и упрощение внутренней архитектуры платёжного модуля.

## Цель

Доработать существующую интеграцию YooKassa без потери текущей функциональности.

Основные задачи:

1. исправить пользовательский сценарий отменённого платежа;
2. использовать `cancellation_details` YooKassa для определения причины отмены;
3. показывать пользователю корректное сообщение для конкретной причины;
4. при отмене создавать новый Payment и новую ссылку оплаты вместо использования старого `confirmation_url`;
5. отрефакторить перегруженный `PaymentService`;
6. проверить структуру таблицы `payments`;
7. проверить архитектуру всего платёжного модуля и упростить её там, где это возможно;
8. сохранить существующую функциональность и идемпотентность webhook.

## Источники истины

Перед изменениями изучить существующую реализацию платёжного модуля.

Документация YooKassa:

`docs/yookassa/declined-payments.md`

используется как источник истины для:

- причин отмены платежей;
- `cancellation_details.party`;
- `cancellation_details.reason`;
- пользовательских сценариев для отклонённых платежей.

Документация тестового магазина:

`docs/yookassa/test-payment.md`

используется для проверки тестовых платежей.

Для API и SDK также учитывать существующую документацию проекта и
установленную версию YooKassa SDK.

## Текущее проблемное поведение

При переходе Payment в `canceled` пользователь получает:

> ❌ Платёж отменён. Вы можете попробовать оплатить ещё раз.

При этом пользователю отправляется кнопка со старым `confirmation_url`.

Старый `confirmation_url` относится к уже отменённому платежу и не должен
использоваться для повторной попытки оплаты.

После перехода по такой ссылке текущий flow может завершаться сообщением:

> ❌ Сейчас не удалось создать платёж. Попробуйте ещё раз позже.

Такое поведение необходимо устранить.

## Целевое поведение

При получении отменённого платежа:

    payment.canceled
          ↓
    cancellation_details
          ↓
    party + reason
          ↓
    определение пользовательского сообщения
          ↓
    локальный Payment → canceled
          ↓
    создание нового Payment
          ↓
    YooKassa createPayment
          ↓
    новый confirmation_url
          ↓
    Telegram:
    причина отмены + новая кнопка оплаты

Старый `confirmation_url` повторно не используется.

## Основные принципы

- webhook остаётся источником истины для статуса платежа;
- отменённый YooKassa Payment не переиспользуется;
- повторная попытка оплаты создаёт новый Payment;
- новый Payment получает новый `yookassa_payment_id`;
- новый Payment получает новый `confirmation_url`;
- причина отмены определяется из `cancellation_details`;
- пользовательское сообщение определяется на основании документации проекта;
- неизвестная причина должна иметь безопасный fallback;
- бизнес-логика не должна дублироваться между Telegram, Controller и webhook;
- рефакторинг не должен менять существующее поведение без явной причины.

## Ограничения

В рамках плана:

- не менять бизнес-правила подписок без необходимости;
- не менять Promocode-логику без необходимости;
- не менять Referral-логику без необходимости;
- не менять Remnawave-интеграцию без необходимости;
- не проводить несвязанный рефакторинг;
- не удалять поля БД без подтверждения отсутствия использования;
- не менять публичные контракты без анализа всех мест использования.

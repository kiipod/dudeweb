# Шаг 3 — Рефакторинг PaymentService

## Зависимости

Перед началом прочитать:

`docs/audit/yookassa-refactoring.md`

Flow отменённых платежей с предыдущего шага должен быть завершён и покрыт
тестами.

## Цель

Уменьшить количество ответственностей `PaymentService` и сделать код:

- проще для чтения;
- проще для тестирования;
- проще для изменения;
- менее связанным;
- без потери существующей функциональности.

## Правила

- не дробить класс ради количества классов;
- каждый новый класс должен иметь понятную ответственность;
- не создавать абстракции без реального применения;
- не создавать interface с единственной реализацией без архитектурной причины;
- не переносить код механически без улучшения структуры;
- не менять публичный API без необходимости;
- не дублировать бизнес-логику;
- существующие тесты должны продолжать проходить.

## Анализ ответственностей

Использовать список из:

`docs/audit/yookassa-refactoring.md`

Для каждой ответственности определить:

- [ ] относится ли она непосредственно к PaymentService;
- [ ] является ли отдельной бизнес-операцией;
- [ ] является ли интеграционной ответственностью;
- [ ] используется ли независимо;
- [ ] усложняет ли она PaymentService;
- [ ] имеет ли собственные зависимости.

## Выделение компонентов

Рассмотреть отдельные ответственности для:

- создания платежа;
- обработки notification;
- canceled/retry flow;
- Subscription activation/extension;
- Promocode processing;
- Referral processing;
- Telegram notification;
- YooKassa mapping.

Это список кандидатов, а не обязательных классов.

Создавать отдельный компонент только если это упрощает архитектуру.

## PaymentService

После рефакторинга PaymentService должен:

- [ ] иметь понятную область ответственности;
- [ ] не содержать чрезмерно длинных методов;
- [ ] не содержать глубокой вложенности без необходимости;
- [ ] не содержать несвязанные side effects в одном методе;
- [ ] не знать детали Telegram UI;
- [ ] не дублировать Promocode-логику;
- [ ] не дублировать Referral-логику;
- [ ] не дублировать Remnawave-клиент.

## Методы

Для каждого большого метода:

- [ ] определить отдельные этапы;
- [ ] уменьшить вложенность;
- [ ] использовать early return там, где это улучшает читаемость;
- [ ] убрать повторяющиеся условия;
- [ ] убрать дублирование;
- [ ] дать методам названия, отражающие бизнес-действие.

## DTO / Value Objects / Enum

Проверить, не передаются ли между методами:

- большие массивы;
- loosely typed payload;
- строки статусов;
- строки `reason`;
- строки `source`.

Использовать существующие DTO/Enum проекта, если они подходят.

Создавать новые только при реальной необходимости.

## Transactions

Проверить границы DB transactions.

- [ ] Определить операции, требующие атомарности
- [ ] Не держать DB transaction открытой во время внешнего HTTP-вызова без необходимости
- [ ] Проверить webhook processing
- [ ] Проверить Subscription
- [ ] Проверить Promocode
- [ ] Проверить Referral

Не менять transaction semantics без понимания текущей логики.

## Error handling

- [ ] Убрать дублирующиеся try/catch
- [ ] Не подавлять исключения без причины
- [ ] Разделить ожидаемые business errors и integration errors
- [ ] Сохранить полезный logging context
- [ ] Не логировать credentials

## Tests

После каждого логического этапа рефакторинга запускать соответствующие tests.

Проверить:

- [ ] создание Payment
- [ ] succeeded webhook
- [ ] canceled webhook
- [ ] retry payment
- [ ] Subscription
- [ ] Promocode
- [ ] Referral
- [ ] Telegram notification
- [ ] webhook idempotency

## Проверка

Сравнить PaymentService до и после.

- [ ] Количество ответственностей уменьшилось
- [ ] Основные public methods понятны
- [ ] Большие методы декомпозированы
- [ ] Дублирование уменьшилось
- [ ] Business flow легче проследить
- [ ] Новые классы имеют реальную ответственность
- [ ] Нет ненужных abstraction layers
- [ ] Поведение payment flow не изменилось
- [ ] Все существующие тесты проходят

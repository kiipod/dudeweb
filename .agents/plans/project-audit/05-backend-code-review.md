# Шаг 5 — Backend Code Review

## Цель

Оценить качество backend-кода, архитектуру,
бизнес-логику, транзакции и обработку ошибок.

Найти неоптимальные участки, которые необходимо исправить
на этапе рефакторинга.

## Архитектура

- [ ] Проверить Controllers.
- [ ] Проверить Services.
- [ ] Проверить Actions.
- [ ] Проверить Handlers.
- [ ] Проверить DTO.
- [ ] Проверить Enums.
- [ ] Проверить Models.
- [ ] Проверить Repositories, если используются.
- [ ] Проверить Events/Listeners.
- [ ] Проверить Jobs/Commands.

## SOLID и ответственность

- [ ] Найти классы с чрезмерной ответственностью.
- [ ] Найти слишком большие методы.
- [ ] Найти дублирующую бизнес-логику.
- [ ] Найти циклические зависимости.
- [ ] Найти избыточные абстракции.
- [ ] Найти классы-прокси без полезной ответственности.
- [ ] Проверить зависимости между слоями.

Не рекомендовать дробление классов только ради уменьшения строк.

## Бизнес-логика

Проверить фактически реализованные сценарии:

- [ ] Регистрация.
- [ ] Trial.
- [ ] Оплата.
- [ ] Продление подписки.
- [ ] Отмена платежа.
- [ ] Промокоды.
- [ ] Реферальная программа.
- [ ] Управление устройствами.
- [ ] User lifecycle.
- [ ] Синхронизация Remnawave.

Проверять сценарии относительно существующих требований.

## Transactions

- [ ] Проверить границы транзакций.
- [ ] Проверить атомарность изменений.
- [ ] Проверить внешние HTTP-вызовы внутри транзакций.
- [ ] Проверить rollback.
- [ ] Проверить повторные запросы.
- [ ] Проверить race conditions.
- [ ] Проверить идемпотентность.

## Database

- [ ] Проверить migrations.
- [ ] Проверить foreign keys.
- [ ] Проверить unique constraints.
- [ ] Проверить relations.
- [ ] Проверить casts.
- [ ] Проверить scopes.
- [ ] Проверить неиспользуемые поля.
- [ ] Проверить избыточное хранение состояния.

Не удалять поля БД на этапе аудита.

## Error Handling

- [ ] Проверить exceptions.
- [ ] Проверить try/catch.
- [ ] Проверить logging.
- [ ] Проверить повторные попытки.
- [ ] Проверить обработку ошибок внешних API.
- [ ] Проверить отсутствие подавленных исключений.

## Refactoring Candidates

Для каждого кандидата определить:

- проблему;
- затронутые классы;
- влияние на поддерживаемость;
- риск изменения;
- необходимое тестовое покрытие;
- предлагаемую архитектуру.

## Findings

Использовать префикс BE.

Не создавать finding только потому, что код отличается
от субъективно предпочтительного стиля.

## Проверка

- [ ] Основные backend-модули проверены.
- [ ] Бизнес-логика проанализирована.
- [ ] Транзакции проверены.
- [ ] БД проанализирована.
- [ ] Refactoring candidates задокументированы.
- [ ] findings.md обновлён.
- [ ] Production-код не изменён.

# frontend-design

## Общая информация

- Путь: `.agents/skills/frontend-design/SKILL.md`.
- Source: `anthropics/skills`.
- Статус: `Available`; CLI обнаруживает skill. Доступность в Codex и
  контейнерный `Agents: not linked` разграничены в [карте выбора](README.md#codex-availability).
- Назначение: формирование осознанного визуального направления для нового UI
  или существенного изменения существующего интерфейса.
- Версия skill в metadata не указана.

Skill рассматривает агента как design lead: визуальные решения должны исходить
из предметной области, аудитории и задачи продукта, а не из повторяемого
шаблона.

## Когда использовать

- При создании страницы, лендинга, dashboard или другого заметного UI с нуля.
- При редизайне, когда нужно определить палитру, типографику, композицию,
  визуальную иерархию, motion и тон текстов.
- Когда пользователь просит сделать интерфейс выразительным, фирменным или
  отличимым от типового SaaS-шаблона.
- При ревью визуальной целостности готового интерфейса.

Примеры запросов:

- «Сделай новую публичную страницу продукта в визуальном стиле бренда».
- «Переработай dashboard, чтобы иерархия стала яснее и дизайн не выглядел
  шаблонным».
- «Предложи и реализуй дизайн-систему для нового frontend-раздела».

## Когда не использовать

- Для чисто backend-задач, миграций БД, API-интеграций и Laravel-рефакторинга.
- Для точечной замены текста, исправления обработчика или другой задачи без
  визуального решения.
- Как источник API Vue, UI-библиотеки или Tailwind: эти детали проверяются по
  специализированному установленному skill либо фактическому package source и
  официальной документации.
- Когда пользователь уже задал точное визуальное направление: skill требует
  следовать brief, а не заменять его собственной эстетикой.

## Возможности

- Вывод визуального языка из предмета, аудитории и основной задачи страницы.
- Проектирование компактной системы цветов, шрифтов, layout и принципов.
- Сравнение вариантов layout через короткие ASCII-wireframes.
- Выявление типовых AI-patterns: безосновательные gradient/card layouts,
  одинаковые скругления, декоративные labels, рассеянные анимации и другие
  решения, не связанные с содержанием.
- Проработка интерфейсного текста: plain language, active voice, единые имена
  действий, полезные error/empty states.
- Самокритика результата через visual review и screenshots, если среда это
  позволяет.

## Основные инструкции

- Если brief не задаёт продукт или аудиторию, сначала предложить конкретный
  вариант и подтвердить его с пользователем.
- Сначала подготовить design plan: 4–6 именованных цветов с hex, выбранные
  typefaces и их роли, layout/alignment и отличительные принципы.
- До реализации проверить план на шаблонность и пересмотреть решения, которые
  не следуют именно этому brief.
- Делать один элемент главным визуальным акцентом, а остальную систему держать
  сдержанной; декоративные элементы должны передавать структуру.
- Не злоупотреблять автоматическими появлениями и hover-анимациями; motion
  должен объяснять изменение или направлять внимание.
- Соблюдать mobile responsiveness, видимый keyboard focus, reduced motion,
  визуальную доступность и разумную длину строк.
- Следить за CSS specificity и не создавать конфликтующие правила.

## Workflow

1. Уточнить предмет, аудиторию, задачу и ограничения brief.
2. Сформировать токены, типографику, layout/wireframes и визуальные принципы.
3. Сравнить план с brief и убрать не обоснованные предметом generic-patterns.
4. Реализовать пересмотренный план средствами стека проекта.
5. Проверить адаптивность, focus, reduced motion, доступность и текст.
6. Провести visual critique, по возможности по screenshots, и убрать лишнее.

## Применимость к проекту

Применимость высокая для новых и существенно изменяемых Inertia/Vue-страниц.
В проекте подтверждены Vue, Inertia и Tailwind. Визуальный план должен
использовать компоненты и токены фактического стека, а не создавать
параллельную CSS-систему. Для backend-задач skill неприменим.

Текущий публичный экран использует распространённую hero/cards/CTA-композицию.
Это не означает автоматическую необходимость редизайна, но при отдельной задаче
на его переработку skill потребует заново обосновать композицию содержанием.

## Пересечения с другими skills

- `vue-best-practices` отвечает за компонентную архитектуру и data flow, а
  `frontend-design` — за визуальное направление и UX.
- `tailwind-best-practices` поддерживает design tokens, utility discipline и
  variants shared components после определения визуальной системы.
- `tailwind-4-docs` проверяет корректность version-specific Tailwind API.
- API UI-библиотеки проверяется по фактически установленному package source и
  официальной документации.

Для полноценной frontend feature эти skills дополняют друг друга; один
`frontend-design` не задаёт корректную Vue-архитектуру или component API.

### Специализация и совместное использование

Для категории UI/UX design это наиболее специализированный установленный
skill. Он нужен без остальных, когда результатом является только design plan
или visual critique без кода.

Для полноценной frontend feature обоснована комбинация:

1. `frontend-design` связывает visual direction с brief и content.
2. `vue-best-practices` определяет component map, state и contracts до code.
3. `tailwind-best-practices` проверяет tokens, class lists и component variants.
4. API фактически установленной UI-библиотеки проверяется по её source/docs.
5. `tailwind-4-docs` проверяет version-specific custom styling только при
   наличии актуального snapshot.

Не каждый пункт обязателен для каждого изменения: например, точечный Vue bug
без visual change не требует нового design plan, а feature без
version-specific Tailwind concern не требует `tailwind-4-docs`.

## Приоритет инструкций

Сам `SKILL.md` явно говорит, что точные слова пользовательского brief имеют
приоритет над эстетическими предпочтениями skill. Архитектурные и стековые
ограничения проекта задаются `AGENTS.md`; skill не отменяет Composition API,
подтверждённый UI stack, Tailwind 4 или Inertia flow.

## Ограничения и риски

- Skill даёт design judgment, но не API-справочник конкретной библиотеки.
- Без конкретного brief требуется пользовательское подтверждение предложенной
  предметной области; иначе визуальная концепция будет основана на допущении.
- Стремление к отличимости не отменяет доступность, responsiveness и
  согласованность с существующим продуктом.
- Screenshot review зависит от возможностей окружения и не гарантируется.
- Generic card/layout examples из других frontend skills могут противоречить
  требованию предметной уникальности. Это не API-конфликт: готовые components
  допустимы, если их композиция обоснована brief.
